# Automatic backup interruption investigation — 2026-09-29

## Evidence and confidence

Production files were inspected read-only. No production backup, state, temporary file, installed
script or task was modified. Repository/installed v1.0 src SHA-256 values matched before editing.

`backup.log` records 22 saves at T+00:00, followed by 19 UNCHANGED and 2 CHANGED records
(both CHANGED are TITLE_B), with no final summary or ERROR. `monitor.log` records exit 1 at
T+00:26. An earlier and a later automatic attempt also ended without a summary. A subsequent
manual run completed with 22 UNCHANGED and zero failures.

Preserved temporary ZIPs and extracted directories have matching interruption timestamps:

| Time | Temporary basename | Extracted files | V4 hash matches current state entry |
| --- | --- | --- | --- |
| earlier attempt | TEMP_C | 5 | TITLE_C / SAVE_C |
| T+00:26 | TEMP_A | 8 | TITLE_A / SAVE_A |
| later attempt | TEMP_D | 5 | TITLE_D / SAVE_D |

Hashes were computed from existing extracted files without extracting/deleting production data.
The comparison is to the **current** state after the successful manual run, not a historical state
snapshot. These artifacts support completed download/extraction of the next unlogged save, including
the 22nd save in the main attempt. They do not preserve the original exception or prove hashing completed then.

## Reproduced failure point

On this Windows PowerShell 5.1 environment, hold a read handle with the exact flags used by
`History.ReadTail`: FileAccess.Read, FileShare.ReadWrite | FileShare.Delete. `Add-Content -Encoding
UTF8 -ErrorAction Stop` on that file throws GetContentWriterIOError / IOException (sharing violation).
Permissive sharing on the reader alone does not solve the writer's denial of existing readers.

The full engine was reproduced with a deterministic reader acquired during the final fixture
download. Before the fix it returned **1**, left only the earlier save result in backup.log, and
printed **no BACKUP COMPLETE**. Its console showed the sharing exception and
`(log could not be written)`. The outer catch retried the same incompatible logger, so its diagnostic
also failed to persist. This reproduces the observed signature without a PS4 or network request.

In the UNCHANGED branch, `Write-Log` occurs **before** the counter increment and temporary cleanup.
A log exception there leaves both ZIP and extraction directory. The exception is not handled by
the download/hash catches; it reaches the outer catch and exits 1. NEW/CHANGED also log after
publishing the ZIP and committing state, so a log error can interrupt reporting after safe publication.

**Confirmed:** the integration defect and its deterministic engine reproduction. **Strongly supported,
not conclusively recovered:** this was the exception in the historical T+00:00 run. No persisted stdout/
stderr or stack trace for that run exists in the inspected installation. HiddenProcess retains only
20 lines in memory; later runs/restarts lose that evidence. Do not label historical causation proven.

## Other paths reviewed / automatic versus manual

- Ordinary download/hash failures are caught per save, counted and normally produce a summary and
  exit 20. Failures while logging/cleaning up inside those catches can instead reach the outer catch.
- Name/path handling, final directory creation, ZIP move, atomic state publication and temporary
  cleanup can throw to the outer catch. No evidence warrants changing these operations or retrying them.
- Cleanup after the 21st result could explain 21 lines alone, but the T+00:26 final-save temporary
  extraction provides additional evidence for processing the 22nd save.
- State commits occur after each published changed/new ZIP. All-UNCHANGED runs do not rewrite state
  and finish with **0**, never 1 as a synonym for no changes.
- Automatic invocation is `& Backup-PS4.ps1 -ConfigPath ...` within the hidden monitor's PowerShell
  process, reporting LASTEXITCODE into monitor.log. Check saves now launches the same engine with
  the same config in a separate hidden PowerShell process and reads its process exit code.
- Both paths run while the GUI polls backup.log every two seconds. Either can hit the logging race;
  a later successful manual run does not establish that automatic backup uses a different algorithm.

## Changes and preservation

`Common.ps1` adds `Add-AppLogLine`, an append-only UTF-8 StreamWriter with explicit ReadWrite
sharing and deterministic disposal. `Backup-PS4.ps1` and `Monitor-PS4.ps1` change **only their log
append calls**. The monitor also needs this because the GUI now reads its log. Real write failures
still propagate; the fix does not swallow errors or pretend a failed backup succeeded.

`History.cs` parses nonzero automatic exits and execution exceptions from bounded monitor.log tails.
`ActivityEntry.cs` and `MainWindow.xaml.cs` merge failed attempts with summary results chronologically
(three visible, ten in Diagnostics). Codes appear in Diagnostics; failures carry no fabricated counts.
The last completed backup panel remains sourced only from backup summaries. Repeated refreshes rebuild
the same list, and restart recovers attempts from the existing log without a new state file.

No migration/reset of configuration, save state, backups or history is needed. No new automatic retry
or change to OFF/ON rearming is introduced. Existing release packaging includes the updated scripts;
build with `powershell -NoProfile -ExecutionPolicy Bypass -File build/Publish-Gui.ps1 -SelfContained`,
then exit the existing tray application and launch the fully extracted new package. This investigation
does not install it into the user's live session. No commit, tag or push is performed.

Automated tests cover a reader held through the final NEW and UNCHANGED save, successful summary/

malformed/partial records), bounded history, refresh stability and UI preservation of the last result.
Run `tests/Run-Tests.ps1` and `build/Test-Gui.ps1` under Windows PowerShell.

Real PS4 validation of the fix is **PASS** (owner-reported 2026-09-29; results in validation.md). The following checklist remains available for future verification:

1. Exit the old tray application after any backup finishes; launch the updated extracted package.
2. Keep the main window open so history polling runs. Verify existing history and the T+00:00 failure
   in Diagnostics (subject to the 128 KiB tail limit and ten-entry display limit).
3. Keep Apollo off for at least 12 seconds; enable its web server and wait for the automatic check.
4. Verify all discovered saves have outcomes, the final summary exists, and monitor.log reports
   success. An all-UNCHANGED check must complete with exit 0 and no new versions/state rewrite.
5. Modify a save in a game, reopen Apollo after an OFF interval, and verify only changed content
   creates versions. Run Check saves now afterwards and verify normal UNCHANGED completion.
6. If any nonzero automatic exit recurs, preserve both logs and temporary artifacts, inspect
   Diagnostics, and verify the failed attempt is visible while the last completed counts remain.
   Do not delete state or saves to investigate.

Limitations: the original exception cannot be reconstructed with certainty; older records outside the
bounded tail are not shown; a process killed before monitor writes an outcome cannot be inferred as a
failed attempt; a summarized partial run can show both summary and automatic exit records.
